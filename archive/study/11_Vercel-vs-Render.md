# Vercel은 프론트만, Render는 API만 하게 하는 이유

핵심은 **역할 분리** 때문입니다.

### 왜 분리하나요?

1. **각 플랫폼이 잘하는 일이 다름**
   - **Vercel**: HTML/CSS/JS 같은 **프론트 배포**에 강함
   - **Render**: Python/FastAPI 같은 **백엔드 서버 실행**에 적합

2. **배포와 수정이 편해짐**
   - 프론트만 바꾸면 **프론트만 다시 배포**
   - 백엔드만 바꾸면 **백엔드만 다시 배포**
   - 서로 영향이 적음

3. **성능이 좋아짐**
   - 프론트는 CDN으로 빠르게 제공
   - 백엔드는 API 요청만 처리해서 역할이 명확함

4. **확장하기 쉬움**
   - 사용자가 많아지면 프론트 트래픽과 API 트래픽을 따로 관리할 수 있음

5. **보안/환경변수 관리가 쉬움**
   - API 키, DB 비밀번호는 **백엔드(Render)** 에만 두고
   - 프론트(Vercel)에는 노출하지 않음

---

### 한 줄 정리
**Vercel은 화면 보여주는 데 최적화**,  
**Render는 서버 로직 처리에 최적화**라서  
보통 **프론트와 백엔드를 분리**합니다.

# Vercel(프론트)과 Render(백엔드)분리했을 때 프론트가 백엔드 API를 어떻게 호출하는가?

Vercel(프론트엔드)과 Render(백엔드)를 분리하여 배포했을 때, 프론트엔드가 백엔드 API를 호출하는 핵심 원리는 백엔드의 실제 배포 주소(URL)를 환경 변수로 등록하고, fetch나 axios를 통해 HTTP 요청을 보내는 것입니다.
이 과정에서 CORS 에러와 보안을 해결하는 가장 표준적인 2가지 방법을 정리해 드립니다.

------------------------------

## 방법 1: 환경 변수(Environment Variable) 사용하기 (가장 보편적)

백엔드 주소를 코드에 직접 적으면(하드코딩) 보안에 취약하므로, Vercel 환경 변수에 주소를 등록하고 호출하는 방식입니다.

1. Vercel 설정

   1. Vercel 대시보드에서 해당 프로젝트로 이동합니다.
   2. Settings -> Environment Variables 탭을 클릭합니다.
   3. Key에 NEXT_PUBLIC_API_URL (Next.js 기준) 또는 VITE_API_URL (Vite 기준)을 입력합니다.
   4. Value에 Render에 배포된 백엔드 주소(예: https://onrender.com)를 입력하고 저장합니다.

2. 프론트엔드 코드에서 호출

```js
// Vite(React) 예시
const API_URL = import.meta.env.VITE_API_URL;

// Next.js 예시
// const API_URL = process.env.NEXT_PUBLIC_API_URL;

async function fetchData() {
  const response = await fetch(`${API_URL}/api/users`);
  const data = await response.get();
  return data;
}
```

⚠️ 주의 (Render CORS 설정 필수):
이 방식으로 호출하면 브라우저에서 프론트 도메인(Vercel)과 백엔드 도메인(Render)이 달라 CORS 에러가 발생합니다. 따라서 Render 백엔드 코드(Node.js, Spring Boot 등)에서 Vercel의 프론트엔드 주소를 허용(CORS 허용)해 주는 설정을 반드시 추가해야 합니다.

------------------------------

## 방법 2: Vercel Rewrite 기능으로 프록시(Proxy) 설정하기 (추천)

프론트엔드 주소 뒤에 /api를 붙여 호출하면, Vercel 서버가 이를 가로채 Render 백엔드로 요청을 전달(프록시)해 주는 방식입니다. 브라우저는 프론트엔드와 통신하는 것으로 인식하므로 CORS 에러를 원천 차단할 수 있습니다.

1. `vercel.json` 파일 생성
프론트엔드 프로젝트 최상위 루트(Root) 디렉토리에 `vercel.json` 파일을 만들고 아래 코드를 작성합니다.

```json
{
  "rewrites": [
    {
      "source": "/api/:path*",
      "destination": "https://onrender.com*"
    }
  ]
}
```

* https://onrender.com 부분에 본인의 Render 배포 주소를 넣으세요.

2. 프론트엔드 코드에서 호출
따로 도메인을 붙일 필요 없이 상대 경로로 깔끔하게 호출하면 됩니다.

```js
// 브라우저는 자동으로 자신의 Vercel 도메인 뒤에 /api/users를 붙여 요청합니다.
// Vercel 서버가 이 요청을 Render 백엔드로 토스해 줍니다.
fetch('/api/users')
  .then(res => res.json())
  .then(data => console.log(data));
```

------------------------------

## 요약 및 추천

* 백엔드 코드를 직접 수정하기 번거롭거나 CORS 설정을 복잡하게 하고 싶지 않다면 방법 2(Vercel Rewrite 프록시)를 사용하는 것이 가장 깔끔하고 안전합니다.
* Render의 무료 티어는 일정 시간 요청이 없으면 서버가 잠드는 Cold Start(정지 상태) 현상이 있어 첫 API 호출 시 50초 이상 걸릴 수 있으므로 참고하세요.

현재 프론트엔드 프레임워크로 React(Vite)를 쓰시나요, 아니면 Next.js를 쓰시나요? 알려주시면 해당 환경에 딱 맞는 맞춤형 코드로 더 자세히 안내해 드릴게요!

# Render.com는 서버를 제공하는 공간

결론부터 말씀드리면, Render.com은 24시간 내내 켜져서 요청을 기다리는 '진짜 서버(웹 서비스)'를 제공하는 공간이 맞습니다. 이해를 돕기 위해 Vercel(서버리스)과 Render(일반 서버)의 차이를 아주 쉽게 비유로 정리해 드릴게요.

------------------------------

## 1. Render.com은 서버인가요? ➡️ 네, 전통적인 의미의 '컴퓨터 서버'입니다.

우리가 식당을 차릴 때 건물(공간)을 통째로 빌려서 24시간 오픈해 두는 것과 같습니다.

* 작동 방식: 내가 만든 Node.js, Python 같은 백엔드 프로그램이 Render가 제공하는 가상 컴퓨터 안에서 24시간 동안 계속 켜진 상태(대기 상태)로 돌아갑니다.
* 장점: 웹소켓(Websocket) 통신처럼 클라이언트와 계속 연결을 유지해야 하는 기능(실시간 채팅 등)이나, 백엔드 내부 메모리에 데이터를 잠시 보관하는 등의 작업이 부드럽게 잘 됩니다.
* 단점: (무료 플랜의 경우) 아무도 안 오면 전기세를 아끼려고 컴퓨터를 강제로 재우기 때문에, 다시 깨울 때 50초씩 걸리는 단점이 있습니다.

------------------------------

## 2. Vercel의 Serverless Function은 무엇인가요? ➡️ 필요할 때만 켜지는 '마법의 함수'입니다.

식당 건물을 빌리는 게 아니라, 손님이 배달 주문을 할 때만 출장 요리사를 불러서 요리하게 하고 바로 퇴근시키는 방식입니다.

* 작동 방식: 24시간 켜져 있는 서버가 없습니다. 프론트엔드에서 API 요청을 보낸 그 순간에만 Vercel이 컴퓨터를 아주 잠깐(밀리초 단위) 켜서 백엔드 함수(코드)를 딱 한 번 실행하고 결과를 보낸 뒤 컴퓨터를 바로 꺼버립니다.
* 장점: 서버가 잠들어서 50초씩 기다려야 하는 현상이 전혀 없습니다. 언제 찔러도 몇 밀리초 만에 즉시 응답합니다. 게다가 요청이 없을 때는 자원을 전혀 안 쓰기 때문에 무료 제한량이 매우 넉넉합니다.
* 단점: 컴퓨터가 켜졌다 바로 꺼지기 때문에 실시간 채팅(웹소켓)처럼 연결을 유지하는 기능은 구현하기 어렵고, 데이터베이스 연동 시 매번 새로 연결해야 해서 세밀한 설정이 필요합니다.
* '서버리스(Serverless)'라는 이름 때문에 물리적인 서버(컴퓨터)가 아예 없다고 오해하기 쉽지만, 실제로는 서버가 존재합니다. 말씀하신 대로 Vercel이 관리하는 컴퓨터(서버)가 내부적으로 내 백엔드 코드를 실행하는 것이 맞습니다. 그렇다면 왜 컴퓨터가 있는데도 '서버가 없다(Server-less)'고 부를까요? 개발자 입장에서 "내가 직접 관리하고 신경 써야 할 서버 컴퓨터가 없다"는 뜻에서 붙여진 이름입니다. 전통적인 서버 방식과 비교하면 이해하기 쉽습니다.

------------------------------

## 🔄 한눈에 비교하는 선택 가이드

| 비교 항목 | Render.com (일반 서버) | Vercel Serverless (서버리스) |
|---|---|---|
| 서버 유지 방식 | 24시간 항시 대기 (컴퓨터 구동) | 요청이 올 때만 순간적으로 실행 후 종료 |
| 무료 플랜 지연 | 15분간 요청 없으면 잠듦 (깨어날 때 ~50초) | 잠드는 현상 없음 (언제나 즉시 응답) |
| 추천 기능 | 실시간 채팅, 긴 작업, 일반적인 REST API | 간단한 데이터 조회/저장 API, 로그인 처리 |

따라서 만약 만들고 계신 API가 실시간 통신이 필요 없고 단순한 데이터 입출력 위주라면 Vercel의 Serverless 기능을 쓰는 것이 로딩 지연이 없어서 사용성이 훨씬 좋습니다. 반면, 전통적인 방식의 백엔드 아키텍처 구조를 있는 그대로 올리고 싶다면 Render.com이 직관적이고 편합니다.
혹시 지금 구상 중이거나 만들고 계신 백엔드 프로젝트에 실시간 채팅, 알림, 또는 결제 같은 특수한 기능이 포함되어 있나요? 프로젝트 성격에 맞춰 둘 중 어떤 환경이 더 유리할지 짚어드릴 수 있습니다.

'서버리스(Serverless)'라는 이름 때문에 물리적인 서버(컴퓨터)가 아예 없다고 오해하기 쉽지만, 실제로는 서버가 존재합니다. 말씀하신 대로 Vercel이 관리하는 컴퓨터(서버)가 내부적으로 내 백엔드 코드를 실행하는 것이 맞습니다.
그렇다면 왜 컴퓨터가 있는데도 '서버가 없다(Server-less)'고 부를까요?
개발자 입장에서 "내가 직접 관리하고 신경 써야 할 서버 컴퓨터가 없다"는 뜻에서 붙여진 이름입니다. 전통적인 서버 방식과 비교하면 이해하기 쉽습니다.

## 1. 일반 서버(Render) vs 서버리스(Vercel) 차이

* 전통적인 서버 (Render.com 등):
개발자가 가상 컴퓨터 공간을 통째로 임대하는 개념입니다. 서버가 24시간 내내 켜져 있고, 사용자가 한 명도 안 들어와도 전기세(비용)가 나가며, 사용자가 갑자기 100만 명으로 늘어나면 컴퓨터 사양을 직접 업그레이드(스케일 업)해 주어야 합니다. 즉, 개발자가 '서버라는 컴퓨터 공간'을 계속 인지하고 관리해야 합니다.
* 서버리스 (Vercel Serverless):
개발자는 컴퓨터 자체를 아예 신경 쓰지 않습니다. 오직 내가 짠 백엔드 함수(코드)만 Vercel에 던져줄 뿐입니다. 평소에는 컴퓨터가 완전히 꺼져 있다가, 요청이 들어오는 순간 Vercel이 알아서 남는 컴퓨터 자원을 쪼개어 코드를 실행하고 바로 꺼버립니다. 사용자가 100만 명으로 늘어나면 Vercel이 알아서 컴퓨터 100만 대를 순간적으로 켜서 처리합니다.

------------------------------

## 2. 핵심은 '인프라 관리의 주체'가 누구인가

서버리스라는 명칭은 기술적 구조가 아니라 개발자의 경험에서 나온 단어입니다.

* Server-full (전통 방식): 서버 인프라(OS 업데이트, 메모리 관리, 포트 설정, 서버 가동 유지)를 개발자가 관리함.
* Server-less (서버리스): 그 모든 귀찮은 서버 컴퓨터 관리를 Vercel 같은 플랫폼이 100% 대신 해줌. 개발자는 서버가 몇 대가 도는지, 사양이 얼마인지 알 필요도 없고 알 수도 없음.

즉, "내 눈앞에 관리해야 할 서버가 보이지 않는다"는 의미에서 Serverless라고 부르는 것입니다. 실제 밑바닥에서는 Vercel이 거대한 데이터 센터의 컴퓨터들을 아주 정밀하게 쪼개서 우리 코드를 잠시 실행시켜 주고 있는 것이죠.
Vercel의 이 편리한 서버리스 함수를 활용해 백엔드를 구축해 보고 싶으신가요? 현재 어떤 언어나 프레임워크(Node.js, Next.js 등)를 다루고 계시는지 말씀해 주시면 Vercel 배포에 필요한 가이드를 드릴 수 있습니다.
